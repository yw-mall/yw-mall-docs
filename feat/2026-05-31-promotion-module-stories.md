# 优惠活动模块 Story 拆分 + 工期预估 · v0.1

> 配套 PRD: [2026-05-31-promotion-module-design.md](./2026-05-31-promotion-module-design.md)
> 估算单位：**人天** (1 人 / 1 工作日，含设计+开发+自测，不含联调/集成/Code Review)
> 经验系数：实际工期 ≈ 估算 × 1.4（含联调 / Bug Fix / 文档 / 部署）

---

## 估算说明

- **粒度**：每个 story 1-5 人天为佳；>5 人天必须拆
- **角色**：BE = 后端 Go / FE = 前端 Vue / DB = SQL 模型 / QA = 测试 / PM = 产品验收
- **依赖标记**：`→` 表示前置依赖
- **风险等级**：🟢 标准 / 🟡 有不确定性 / 🔴 高风险（如算法/性能）

### 关键依赖路径（不能压缩）

1. **价格引擎（S1.4.1-6, 15 人天）** —— Phase 1 的瓶颈，决定后续所有活动类型能否正确叠加。建议派 1 高级 BE 专职 3 周。
2. **秒杀异步落库（S2.1.5）** —— Phase 2 高并发硬骨头，需要 Kafka + 容错 + 压测验证。
3. **跨店满减（4.1）** —— Phase 4 算法最难，是双 11 / 618 的核心能力。

### 推荐切入节奏

1. **Week 1**：定 Phase 1 详细技术方案 + DDL + proto 评审；同时跑用户调研把"待决策的 4 个产品问题"敲定
2. **Week 2-4**：Phase 1 主体开发；每周一个 demo day
3. **Week 4 末**：Phase 1 上线 + 内部商家试用 1 周收反馈
4. **Week 5-7**：Phase 2 开发；秒杀模块同步做压测；S2.1.3 单独冲刺

## 风险与不确定性

### 🔴 高风险项（必须重点关注）

1. **价格引擎正确性**（S1.4）—— 互斥/叠加规则一旦算错就是真金白银的客诉。**强制 TDD，单元测试覆盖率 >90%**。
2. **秒杀高并发**（S2.1.3/5/9）—— 一个 bug 可能直接超卖几万件。**必须压测 + 灰度发布**。
3. **退款分摊算法**（S1.6.2）—— 用户和商家都会算账，规则必须能向客服讲清。**配套写一个"退款分摊计算器" 内部工具**。

### 🟡 中等风险（需关注）

1. **会员等级迁移**（S3.1.8）—— 上线时历史用户回填等级要充分测试
2. **积分抵现的财务对账**（S3.2.4）—— 与钱包对账要清晰
3. **券与库存的最终一致性**（S1.5）—— 锁券 / 释放 / 核销三个动作的分布式事务

### 估算偏差

- 实际工期通常比估算 **超 20-30%**，建议在每个 Phase 末预留 1 周 buffer
- Phase 1 是新模块从 0 到 1，**架构成本会比单纯功能开发多**，估算其实偏保守
- 风险项（🔴）的实际工期可能是估算的 1.5-2 倍
