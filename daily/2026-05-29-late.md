## 🐛 用户走查报告的 5 个 bug & 修复

### Bug #1: C 端下单错误提示永远是 "请求失败"

**症状**：`POST /api/order/create` 无默认地址时，FE toast 显示固定 "请求失败"，
而不是后端 `errors.New("请先添加默认收货地址")` 的真实文案。

**根因**：`mall-api/internal/handler/errors.go` 已经有 `writeBizError` 把 err 解包
成 `{code, message}` JSON，但只在 4 个 handler（authlogin / registerv2 / resetpassword
/ sendcode）手工 wire 上。其它 handler（createorder 等）沿用默认 `httpx.ErrorCtx`
→ go-zero 把 `err.Error()` 当 plain text body 写 400，FE `body.message` 读不到
就 fallback "请求失败"。

**修复**（单一来源）：
1. `errors.go` 拆出 `BizErrorHandler(ctx, err) (int, any)` 签名匹配 go-zero 的
   `httpx.SetErrorHandlerCtx`；`writeBizError` 留作 thin wrapper 兼容老 4 个
   callsite，不动它们减小爆炸半径
2. `mall.go` 启动时 `httpx.SetErrorHandlerCtx(handler.BizErrorHandler)` 注册全局
3. BizErrorHandler 优先识别 `errorx.CodeError`（已自带 code+msg）按 code 映射
   404/401/500；否则按 gRPC status 映射；都没有就 400 + ParamError
4. `createorderlogic.go` 改用 `errorx.NewCodeErrorMsg(OrderAddressRequired, ...)`
   —— code 5004 在 errorx spec 里早就声明了，FE 后续能按 code 精准跳「添加地址」

**e2e**：alice `is_default=0` 后下单返 `{"code":5004,"message":"请先添加默认收货地址"}` ✓

**副作用**：mall-api 所有 handler 现在统一返 JSON 错误体，FE 错误提示从这次开始
全链路真实可读（之前只有 4 个 handler 有此待遇）。

### Bug #2: 商家后台看不到 C 端新下的订单

**症状**：用户 C 端下单（order id=19）后，商家管理后台「订单管理」和「财务」
都查不到该订单。

**根因链**：
1. `mall-order-rpc/createorderlogic.go` 的 INSERT 语句**漏写了 shop_id 列** →
   所有订单 shop_id=0
2. 商家后台 `ListShopOrders` 用 `WHERE shop_id=?` 过滤 → 永远查不到
3. `ConfirmMockPay` 用 `if row.ShopId > 0` 守卫钱包/流水写入 → shop_id=0 的订单
   付款后 wallet 和 ledger 也是空的
4. **顺带暴露老 bug**：`ListShopOrders` SQL 只 SELECT 13 列但 `orderRow` 结构体
   18 字段，go-zero sqlx 报 "not matching destination to scan"。之前因 shop_id=0
   返空集没触发循环，scan 永远不进 case，所以 M3 至今没被发现

**修复**：
1. `mall-order-rpc` 接入 `ProductRpc`（项目既定的跨服务依赖模式）：go.mod replace /
   config / yaml / svc 四件套
2. `CreateOrder` 反查首件商品 → `product.shop_id`，写到 INSERT
3. 多 item 同店校验（单店购物车模型；多店购物车需另跑拆单逻辑，目前明确拒绝）
4. `ListShopOrders` SQL 改用 `orderTimelineCols` 对齐 orderRow 18 字段
5. **DB 手动 backfill** 历史 10 条 `shop_id=0` 订单：
   ```sql
   UPDATE mall_order.`order` o
   JOIN (SELECT order_id, MIN(product_id) pid FROM mall_order.order_item GROUP BY order_id) oi ON oi.order_id = o.id
   JOIN mall_product.product p ON p.id = oi.pid
   SET o.shop_id = p.shop_id WHERE o.shop_id = 0;
   ```

**e2e**：
- 新订单 21 INSERT 后 `shop_id=1` ✓
- mock-pay → wallet `frozen=9900`、ledger entry `{category:"order_income", amount:9900, orderId:21}` ✓
- 商家订单列表能看到 order 21 + 19 ✓

**注意**：历史 paid 订单的 wallet.frozen / ledger 不会自动补回（当时 ConfirmMockPay
已 skip），如需重算需要另跑数据脚本，但属于 dev 历史脏数据范畴，不影响新流程。

## 🔑 心得

### "最合适的修复" 这次又派上了用场

- **Bug #1** 我本来可以只在 createorderhandler 里手 wire 一个 `writeBizError`
  call，5 秒搞定。但那是补丁式 fix —— 下一个 handler 还会有同样问题。
  正路是注册全局 handler，让所有 handler 一次性受益。
- **Bug #2** 我可以只 backfill order 19 一条记录让用户看到，但根因
  `createorderlogic.go` INSERT 漏列才是真正的问题。修代码 + backfill 历史，新订单
  自动正确，旧订单也不留尾巴。

### LSP 红线不等于编译错误

改了 proto 重新 regen pb.go 之后，IDE diagnostic 立刻报 `undefined: OrderNoKw`
这种"字段不存在"。第一反应想去清缓存或重启 gopls。但其实直接 `go build ./...`
是 success —— 编译器读的是 disk 上最新的 pb.go，diagnostic 用的是 LSP 缓存的
旧版。**先跑 build 验真，再决定有没有 bug**。

### "顺带暴露老 bug" 的连环效应

Bug #2 修了 shop_id 写入后，立刻把另一个 M3 时期就存在的 SQL bug（13 列 SELECT
vs 18 字段 struct）暴露出来。**老 bug 之所以"老"，往往是因为别的 bug 把它压住了**。
修了一个，下一个自然浮出。所以 e2e 必须每次完整跑一遍，不能只测自己改的那一段。

### 跨服务字段传递的 3 层漏斗

Bug #3 暴露了一个常见的"字段透传漏斗"模式：
proto 有 → RPC pb 有 → RPC logic append 漏 → admin-api types 漏 → admin-api
transformer 漏 → FE 显示空。每一层都可能丢字段。**改了 proto 后，必须沿调用链
逐层 grep**，不能假设上游加了下游就能拿到。
