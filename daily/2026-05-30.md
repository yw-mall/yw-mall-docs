### 路径 3: 退款执行完成的副作用 (M4)

退款 3 类工作流的执行点（仅退款 approve / 退货退款 inspect pass / admin
仲裁 / 换货 ship）跑完后的状态一致性。

**bug A**: 4 个完成点全部没同步 `order.status` —— refund_request status=4
（已退款）但 `order.status` 仍是 1（已付款），商家「订单管理」误显示
"待发货"，UX 严重错乱。

**bug B**: `ExecuteRefund` 把 `total_income -= amount`，把「累计入账」单调
计数器打成负数。total_income 是 gross income（设计上结算时累加），
退款额应该走另一个维度。

**修**：
1. refundhelpers.go 加 `markOrderAsRefunded(ctx, conn, orderId, reason)`
   helper：UPDATE order SET status=4, cancel_time=now, cancel_reason=?
   WHERE id=? AND status NOT IN (3,4)。NOT IN 防呆：已完成订单不被退款
   回滚到取消、已取消订单不重复打 cancel_time
2. 4 个完成点都调用 helper，reason 区分：
   - 仅退款 approve → `refund:approved`
   - 退货退款 inspect 通过 → `refund:return-passed`
   - admin 仲裁通过 → `refund:arbitrate`
   - 换货发货 → `refund:exchange`
3. executerefundlogic.go 去掉 `total_income = total_income - ?` 一段，
   只动 frozen 扣减

e2e: alice 下单 25 (¥50) → mock-pay → 仅退款 → 商家 approve
- order.status: 1 → 4 (cancel_reason='refund:approved') ✓
- refund.status: 0 → 4 ✓
- wallet.total_income: 0（不被污染）✓
- wallet.frozen: -5000 ✓

### 路径 4: 退货退款 (refundType=2) / 换货 (=3) 流程 (M4)

接路径 3，跑完整的多步骤流程才发现：

**bug**: `MerchantHandleRefund` **不论 refundType 是 1/2/3 都直接 ExecuteRefund
+ status=4**。退货退款 approve 时跳过买家寄回 + 商家验货两步，钱直接退给
买家，商家既没收到货也没机会拒收。

**修**：approve 分支按 type 拆：
- type=2 / type=3 → 只 flip status=1，等待下一步（ship-return → inspect /
  ship-exchange）
- type=1 → 走原来的 ExecuteRefund + status=4 完整流程

后续 ship-return / inspect-passed / ship-exchange 步骤在另外的 logic 文件
里已实现，本次只把入口流程拨对方向。

e2e:
- **退货退款 4 步全通**：submit type=2 → approve → ship-return → inspect-pass
  → refund 0→1→1→4, order 2→...→4 (cancel_reason='refund:return-passed') ✓
- **换货 5 步全通**：submit type=3 → approve → ship-return → inspect-pass
  → ship-exchange → 原 order status=4 cancel_reason='refund:exchange' + 新 order
  33 自动创建 status=2 ✓

## 🔑 心得

### 设计意图明明白白，logic 偏偏漏调

`writeLedgerEntry` 签名有 withdrawalId 槽位 / `OrderDetailResp` struct 有
payTime/cancelReason 字段 / `MerchantHandleRefund` 收到 refundType 参数 ——
这些都是设计层面意图清晰的接口，但底下的 logic 偏偏只用了一半。**API
surface 比 implementation completeness 更难审计** —— 修这种 bug 不需要
重新设计，只需要把已经摆好的拼图拼齐。

### "字段透传漏斗"模式反复出现

今晚两次撞同样的模式：
- 路径 2: shop-rpc proto 有 → mall-api logic 漏，因此 C 端拿不到
- 路径 6: order-rpc pb 有 → mall-api types 漏 / mall-api list logic 漏，
  因此 C 端拿不到

下游 RPC 把数据传上来，每过一层 transformer 就有机会丢字段。**API
boundary 是 bug 的高发地带**，因为每一层 transformer 都是手写的 struct
literal，加字段比 RPC 还要繁琐。考虑后续是否做 codegen / 反射工具帮自动
透传——但现阶段一个个手补也 OK，至少 e2e 把它们都暴露出来了。

### 多步骤工作流的 bug 必须 e2e 才能发现

路径 4 的 "MerchantHandleRefund 不区分 refundType" 这种 bug，单元测试很难
发现（因为单元测试通常 fix 一个 type 测一条路径，三类 refund 都各自 OK）。
只有跑完整 4/5 步流程才会发现"咦怎么走到第二步就直接退款了？"。**多步骤
状态机必须按完整 lifecycle 跑 e2e**，单步测试不足够。

### 容器化基建的副作用

测 dashboard 兜底时一开始用 `./start.sh stop`，结果把所有服务都停了。
单测兜底必须用单进程精准杀。这点 start.sh 当前不支持 `stop <service>`
单服务停。**ops 工具链对 e2e 测试的支持还不够细**，后续可以加个 `start.sh
kill <service>` 指令专门用于故障注入测试。
