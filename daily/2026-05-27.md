### 1. 新增 helper：`destroyUserSessionsByRole`

文件：`mall-user-rpc/internal/logic/sessionhelpers.go`（+47 行）

```go
func destroyUserSessionsByRole(ctx context.Context, svcCtx *svc.ServiceContext,
                               uid int64, role string) (int, error) {
    if uid <= 0 || role == "" {
        return 0, nil
    }
    tokens, err := svcCtx.Redis.SMembers(ctx, userSessionsKey(uid)).Result()
    if err != nil && err != redis.Nil {
        return 0, err
    }
    removed := 0
    for _, access := range tokens {
        raw, gerr := svcCtx.Redis.Get(ctx, sessionKey(access)).Result()
        if gerr != nil {
            // 索引还在但 session 已过期 — 顺手把悬挂条目也清掉
            _ = svcCtx.Redis.SRem(ctx, userSessionsKey(uid), access).Err()
            continue
        }
        var sess sessionPayload
        if jerr := json.Unmarshal([]byte(raw), &sess); jerr != nil {
            continue
        }
        if sess.Role != role {                    // ← role 过滤是关键
            continue
        }
        if sess.RefreshToken != "" {
            _ = svcCtx.Redis.Del(ctx, refreshKey(sess.RefreshToken)).Err()
        }
        _ = svcCtx.Redis.Del(ctx, sessionKey(access)).Err()
        _ = svcCtx.Redis.SRem(ctx, userSessionsKey(uid), access).Err()
        removed++
    }
    return removed, nil
}
```

跟现有 `DestroyAllUserSessionsLogic.DestroyAllUserSessions` 的区别只有一点：**按 `sess.Role == role` 过滤**。

## 🤔 为什么按 `role` 过滤，不直接调 `DestroyAllUserSessions`

读 `sessionhelpers.go` 注释 + `CreateSession` 代码确认：

```go
// user_sessions:{uid} SET<access_token>     no TTL
```

```go
// createsessionlogic.go
if err := l.svcCtx.Redis.SAdd(l.ctx, userSessionsKey(in.Uid), access).Err(); ...
```

**`CreateSession` 用的 key 只跟 `in.Uid` 走，不掺 role**。Admin 登录和 c-user 登录都通过同一个 `CreateSession` 路径写到这个 set。

所以现实里：
- `admin_user.id = 1`（种子 admin） + `user.id = 1`（alice）**共享** `user_sessions:1` 这一个 Redis set
- admin 改密时若一锅端调 `DestroyAllUserSessions(1)`：alice 也被踢下线 ❌

按 `sess.Role` 过滤是**不动 proto / 不动 index 布局**的最小侵入修法。代价是每次多一次 GET session JSON，但 N 个 token 也就 N 次 Redis lookup，可忽略。

未来如果要彻底解掉这个 uid 共享 set 的问题，正路是把 key 从 `user_sessions:{uid}` 改成 `user_sessions:{role}:{uid}`，**所有写入和读取点同步迁移**，那是 P1+ 单独工程，不在本次范围。
